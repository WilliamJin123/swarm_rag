## Summary

This phase focuses on running the benchmark infrastructure built in Phase 6, debugging any issues encountered during benchmark runs, and validating that the system meets the 500 generations / 3 hour target. The research identified three categories of work needed:

1. **Immediate issues from recent runs** - Device mismatch errors, memory growth hitting the 85% hard stop threshold
2. **Debugging patterns** - Systematic approaches to diagnose benchmark failures
3. **Validation reporting** - Producing actionable pass/fail reports with root cause analysis

Recent benchmark runs (20260203_*) reveal the benchmark infrastructure works but encounters two failure modes: (1) CUDA device mismatch errors between CPU and GPU tensors, and (2) memory growth that triggers the 85% hard stop threshold before completing even a single generation. The recent commit (88b7f30) addressed some timing anomalies but the device mismatch and memory growth issues remain for full validation.

**Primary recommendation:** Run benchmarks iteratively with reduced scope (fewer generations, smaller population) to isolate failure modes, fix device mismatches in the embedding handler, then scale up to full 500-generation validation.

## Architecture Patterns

### Benchmark Debugging Flow
```
1. Run benchmark with reduced scope
   |
   v
2. Capture failure mode
   |
   v
3. Diagnose from logs (memory.log, evolution*.log)
   |
   v
4. Fix root cause
   |
   v
5. Re-run benchmark
   |
   v
6. If passes: Scale up scope
   |
   v
7. If fails: Return to step 3
```

### Pattern 1: Iterative Scope Escalation
**What:** Start with minimal benchmark settings, scale up only after success
**When to use:** Initial validation or after fixing failures
**Example:**
```python
# Start small (10 gens, 25 population) to verify basic operation
python -m swarm_rag.benchmark.run_benchmark --generations 10 --population 25

# If passes, scale up gradually
python -m swarm_rag.benchmark.run_benchmark --generations 50 --population 50
python -m swarm_rag.benchmark.run_benchmark --generations 100 --population 75
python -m swarm_rag.benchmark.run_benchmark --generations 500 --population 75  # Full target
```

### Pattern 2: Memory Snapshot Debugging
**What:** Take memory snapshots at key points to identify growth sources
**When to use:** When memory warnings/hard stops occur
**Example:**
```python
# In evolution loop, add after each phase:
print(f"After phase X: {torch.cuda.memory_allocated() / 1e9:.2f} GB")
torch.cuda.empty_cache()
print(f"After empty_cache: {torch.cuda.memory_allocated() / 1e9:.2f} GB")
```

### Pattern 3: Device Consistency Verification
**What:** Assert all tensors are on expected device before operations
**When to use:** When device mismatch errors occur
**Example:**
```python
def verify_device_consistency(tensor, expected_device, name):
    """Verify tensor is on expected device."""
    if tensor.device != expected_device:
        raise RuntimeError(
            f"{name} on {tensor.device}, expected {expected_device}"
        )
```

### Anti-Patterns to Avoid
- **Running full 500-gen benchmark immediately after a fix:** Scale up gradually to catch regressions early
- **Ignoring memory warnings:** Warnings indicate problems that will become hard stops
- **Suppressing exceptions to "get results":** Let failures surface to diagnose root causes
- **Modifying threshold values to work around memory issues:** Fix the leak, don't hide it

## Don't Hand-Roll

Problems that look simple but have existing solutions:

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Memory tracking | Custom tensor tracking | torch.cuda.memory_allocated() + MemoryGuard | Already integrated, battle-tested |
| GPU timing | time.time() | torch.cuda.synchronize() + time.perf_counter() | Avoids async timing pitfall |
| Device management | Manual .to() calls everywhere | resolve_device("auto") from utils | Centralized, consistent |
| Threshold enforcement | Custom if-statements | MemoryGuard context manager | Already handles warning/hard-stop |

**Key insight:** The codebase already has memory management infrastructure from Phase 1. Phase 6.5 is about running benchmarks and fixing issues discovered, not building new infrastructure.

## Common Pitfalls

### Pitfall 1: CUDA Device Mismatch
**What goes wrong:** "Expected all tensors to be on the same device, but found cuda:0 and cpu"
**Why it happens:** Embedding handler or tensor creation defaults to CPU while retriever uses GPU
**How to avoid:**
- Verify device in StarkPreComputedEmbeddingHandler when returning embeddings
- Use `.to(device)` on any tensor before GPU operations
**Warning signs:** Error occurs during matrix multiplication or tensor operations

### Pitfall 2: Memory Growth During Initial Population
**What goes wrong:** Memory grows from 70% to 85% during first generation, triggering hard stop
**Why it happens:** Initial population evaluation creates more tensors than steady-state
**How to avoid:**
- Run gc.collect() + torch.cuda.empty_cache() between batches
- Use smaller initial population for first run
- Verify GPU cache eviction (LRU) is working
**Warning signs:** Memory warnings appearing during first generation evaluation

### Pitfall 3: Timing Anomalies (FIXED in 88b7f30)
**What goes wrong:** Some evaluations take 30+ seconds instead of typical 200-600ms
**Why it happens:** gc.collect() was called on every MemoryGuard exit
**How to avoid:** Commit 88b7f30 fixed this - gc.collect() now only runs when memory > 49%
**Warning signs:** Latency spikes in logs (e.g., 12635.1ms, 15307.0ms)

### Pitfall 4: Empty Log Files
**What goes wrong:** evolution.jsonl is empty, no per-generation stats
**Why it happens:** Benchmark crashes before first generation completes
**How to avoid:** Check evolution*.log for error messages before checking jsonl
**Warning signs:** memory.log only has header, no data rows

### Pitfall 5: LRU Cache Not Evicting (FIXED in 88b7f30)
**What goes wrong:** _gpu_cache grows unbounded, consuming memory
**Why it happens:** Original implementation didn't have eviction
**How to avoid:** Commit 88b7f30 added LRU eviction with cache_size=256
**Warning signs:** Steady memory increase correlated with unique query count

```python
import torch

if torch.cuda.is_available():
    allocated = torch.cuda.memory_allocated() / (1024**3)
    reserved = torch.cuda.memory_reserved() / (1024**3)
    total = torch.cuda.get_device_properties(0).total_memory / (1024**3)
    print(f"Allocated: {allocated:.2f} GB")
    print(f"Reserved: {reserved:.2f} GB")
    print(f"Total: {total:.2f} GB")
    print(f"Usage: {allocated/total:.1%}")
```
